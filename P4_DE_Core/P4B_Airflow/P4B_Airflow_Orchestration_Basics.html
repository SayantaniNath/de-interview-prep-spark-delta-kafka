Orchestration, explained simply

P4B · Airflow · Beginner cheat sheet, using the oracle_to_snowflake_customers.py lab as the example

1. What is an orchestrator?

Picture a kitchen manager with a checklist:

1. Chop vegetables
2. Boil rice          (at the same time as step 1)
3. Cook curry         (only after 1 is done)
4. Serve              (only after 2 and 3 are done)
If anything burns → call me
The manager doesn't cook. They make sure each step happens in the right order, at the right time, gets retried if it fails, and that someone is told when something goes wrong. Airflow, Talend, Dagster and Prefect are all kitchen managers.

The checklistDAG

3. The lab DAG as a story

A shop keeps customer details in an old notebook (Oracle). Every night a helper copies only the new or changed entries into a new computer system (Snowflake).

start_run ──► stage_customers ──┐
          └─► stage_addresses ──┴─► validate_and_commit
   (if any of these fail) ──────────► mark_failed
  1. start_run
    Decide what to copy. The helper checks a sticky note: "Last time I copied everything up to Monday 9 p.m." Now it's Tuesday 9 p.m., so tonight's job is the Mon 9 p.m. → Tue 9 p.m. entries. They write "Tuesday's job: in progress" in a logbook.
    Sticky note = watermark (ORCH_CONTROL). Logbook = ORCH_AUDIT.
  2. stage_customers + stage_addresses
    Copy to a waiting tray. Two helpers work at the same time. One copies changed customers, the other changes of address. They put the copies in a waiting tray (staging tables), not the real system yet. If a helper drops the papers halfway, they empty their part of the tray and start over, so nothing gets copied twice.
  3. validate_and_commit
    Check, then file everything at once. The supervisor checks the tray: no duplicates? no blank IDs? does every address belong to a real customer? If everything looks right, they file both piles into the real system and update the sticky note, all in one go. If anything fails partway, nothing is filed and the sticky note stays at Monday.
  4. mark_failed
    If anything went wrong, someone writes "Tuesday's job: FAILED" in the logbook so people know to look into it.

4. The three ideas that matter

Only copy what changedUse the sticky note (watermark): rows where start < LAST_UPDATED_DATE ≤ end.
Retrying is safeSame window on retry, empty the tray (DELETE … WHERE RUN_ID), redo it. This is called idempotent.
All or nothingThe data and the sticky note update in one transaction, or neither updates.
If you can explain these three, you understand this pipeline, and most incremental-load pipelines in any tool.

5. Two weak spots (good interview talking points)

Late-committing rows get missed. An Oracle transaction sets LAST_UPDATED_DATE = 10:00:00 but only commits at 10:00:05, after the extract ran with end = 10:00:02. The next window starts after 10:00:02, so the row is never picked up. Fix: set end = now − a few minutes (a safety lag), or switch to CDC (change data capture, which reads the database's change log instead of timestamps).
Deletes aren't captured. A watermark only finds inserted and updated rows. If a row is deleted in Oracle, Snowflake never hears about it. Fix: soft-delete flags in the source, CDC, or a periodic full comparison.

6. Quick self-check

Q1. stage_addresses fails and Airflow retries it. Does the retry copy a different time window? Why not?

Q2. The customer MERGE succeeds but the address MERGE fails. What is in the target tables afterwards?

Q3. Why are extract, PUT and COPY in one task instead of three?

Answers: (1) No. start_run reuses the window saved in ORCH_AUDIT for this run_id. (2) Nothing new. Both MERGEs and the checkpoint are in one transaction, so it rolls back. (3) The temp CSV exists only on the worker machine that wrote it; another task might run on a different worker.
